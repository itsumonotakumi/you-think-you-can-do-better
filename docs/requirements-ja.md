# インシデントシミュレーター「じゃ、あなたがやってみてよ」企画書

Nov 8, 2026 · @いつもの匠

本書は要件定義段階の仕様書であり、実装は対象外とする。

## コンセプト

製品名は「インシデントシミュレーター『じゃ、あなたがやってみてよ』」、英語名は「You Think You Can Do Better?」とする。中身はアドベンチャーゲームだが、名乗りは訓練ツールにする。実在の事件を下敷きにした架空企業10社で、同じ事件を4つの立場から追体験する。

- 位置づけ：机上演習（TTX）を一人でも回せる形にしたもの。研修・勉強会・個人学習で使う
- 体験の設計：プレイ中は苦しい。判断は常に時間切れ寸前で、間違えるとSNSと報道に叩かれる。最後まで正しく対応しきると、記者会見で質問を受け切る場面や、復旧後の社員の一言で報われる
- 学べること：同じ事件でも、立場によって「正しい一手」が違う。経営者の正解と担当者の正解を両方体験して、組織としての動き方をつかむ
- 常に最新：世間で新しい事件が起きたら、シナリオを差し替え・追加できる構造にする（詳細は「シナリオ更新の仕組み」）
- 前提：実在の企業・人物は登場させない。事件の構造と教訓だけを借りる（詳細は「権利・名誉毀損の配慮」）

### 目的

本製品の目的は、ITセキュリティへの理解を促すことである。具体的には次の3つを狙う。

1. インシデントレスポンス（事故が起きたときの対応）について学ぶ
2. インシデントレスポンスに興味を持つ
3. 事件のときに起きる批判と、それに対する企業の対応を理解できるようになる

実在の企業を批判することは目的としない。

あわせて、次のことを全画面の前提として利用者に伝える。

- このシミュレーターで高得点が取れても、現実の対応が正しいとは限らない。現実の事件は、ゲームより情報が少なく、時間の制約や事情も複雑である
- 採点は学ぶための目安であり、現実の対応の正しさを保証するものではない

### 対象ユーザー

| 区分 | 対象 | 狙い |
| --- | --- | --- |
| 最優先 | 経営者・役員 | 「技術は分からんが」では済まないことを体で知る。一番叩かれるのは経営者だと知る |
| 対象 | 30代以上の会社員（管理職、情シス担当、CSIRTメンバー、セキュリティ担当者） | 自分の立場での動き方と、他の立場の苦しさを知る |
| 対象外 | 学生、若年層、企業のITセキュリティに関わらない人 | 業務上の責任を前提にした内容のため、設計上の対象にしない |

経営者に自分からやらせるために、経営者ロールは「30分前後で終わる」「技術用語なしで遊べる」「終了後に取締役会で使える1枚の振り返りが出る」を必須要件にする。

### トーン：「じゃ、あなたがやってみてよ」

事件が報じられるたびに、外野から「対応が遅い」「なぜすぐ公表しない」と言う人は多い。本製品はそういう人に当事者の席を座らせ、「では、あなたならできますか」と問う。皮肉の矛先は実在の被害企業ではなく、「外野の自分」に向ける。

- タイトル画面：「この事件、あなたは何と投稿しましたか？」と入力させ、エンディングで自分の投稿と自分の対応を並べて表示する
- 開始時の自己診断：「自分なら何時間で公表できると思うか」を予想させ、終了後に実際の所要時間と並べる
- シュールな皮肉の例：公表文を推敷している間に、自分が昔書いた「経営層は何をしているんだ」という投稿にいいねがつき続ける。「セキュリティは経営課題です」と講演したばかりの社長が、その当日にVPNの意味を聞いてくる
- 全クリア後の称号：「外野卒業」。以後、当事者の苦しさが分かる人として扱う

## ロール4種

同じ事件を、4つのロールがそれぞれの権限と情報量で扱う。ロールごとに見える情報と選べる手が違い、役割を越えた行動は減点になる（担当者が独断で公表する、経営者が現場でサーバーを触る、など）。

| ロール | 持っている権限 | 見える情報 | 問われること | 典型的な落とし穴 |
| --- | --- | --- | --- | --- |
| 経営者（社長・代表取締役） | 事業停止、公表、予算、身代金への対応方針、謝罪の責任 | 要約された報告、売上への影響、取引先・株主・報道の反応 | 決断の速さ、説明責任、被害者優先の姿勢 | 「確定してから公表」で遅れる。会見で「被害はない」と断言する |
| 役員・グループ会社社長 | 自部門・子会社の業務判断、親会社への報告、取引先対応 | 自社の業務への影響、親会社からの指示、取引先からの問い合わせ | 報告の精度と速さ、業務継続、部下を守る判断 | 親会社への報告を控える。自社だけの判断で復旧を急がせる |
| セキュリティ部門長・リーダー（CSIRTリーダー） | 対応体制の立ち上げ、外部専門家の手配、担当者への指示、経営への上申 | 技術的な状況と経営の意向の両方 | 技術と経営の翻訳、体制づくり、証拠の保全と復旧の両立 | 全部自分で抜き、上申が遅れる。証拠を残さずに初期化を許す |
| セキュリティ担当者 | ログの確認、端末の隔離、アカウント停止、一次報告 | ログ、アラート、画面、現場の声 | 正確な一次対応、記録、報告ルートを守ること | 電源を落とす。報告を後回しにする。個人のSNSでつぶやく |

各シナリオは4ロール全てで遊べる。全ロールをクリアすると「全視点リプレイ」が解放され、同じ時刻に各ロールが何をしていたかを並べて見られる。

## ゲームシステム

スコアは0点から始める「信頼スコア」の加点制にする。会社の信頼を傷つければ減点、維持すれば少し加点、回復させれば加点、事件前より信頼と売上を伸ばせれば大きく加点する。各判断のあと、点数の理由と根拠のガイドラインを示し、世間の反応として「痛み」も返す。

### 進行フェーズ

各シナリオは次の7フェーズで進む。ゲーム内時計が動いており、行動するたびに時間が消費される。

1. 検知：アラート、通報、クレーム、外部からの指摘などで始まる
2. 初動・封じ込め：端末の隔離、アカウント停止、証拠の保全（電源を切らない、ログを守る）
3. 体制と報告：CSIRTの招集、経営への上申、外部専門家・保険会社・弁護士への連絡
4. 調査：侵入経路、影響範囲、漏えい件数の特定（決めつけず、しかし遅らせず）
5. 通知・公表：個人情報保護委員会への速報・確報、本人通知、警察、所管庁、取引先、プレスリリース、記者会見
6. 復旧：クリーンな環境からの再構築、段階的な再開、二次被害の監視
7. 事後対応：再発防止策、調査報告書の公開、第三者委員会、振り返り

### プレッシャーゲージ（4本）

| ゲージ | 意味 | 悪化する行動の例 |
| --- | --- | --- |
| 被害拡大 | 漏えい件数、暗号化範囲、二次被害 | 封じ込めの遅れ、安易な再開 |
| 炎上度 | SNSと報道の批判の強さ | 公表の遅れ、矛盾する発表、謝罪の不備 |
| 信頼 | 顧客・取引先・社員・株主の信頼 | 隠蔽、責任転嫁、問い合わせ窓口の不備 |
| 体力 | 対応チームの疲弊 | 役割分担なしの役投げ、交代を入れない |

体力が0になると判断ミスが起きやすくなる。「寝ずに頬張る」を選ぶと一時的に進むが、後半で必ず尾を引く。

### 信頼スコアの付け方

| 区分 | 点 | 例 |
| --- | --- | --- |
| 信頼を増やす（売上を伸ばす） | +200〜+500 | 調査報告書と再発防止策を全面公開し、「一番透明な会社」として新規契約が増える。取引先が対応を評価して取引を広げる。得た知見を業界に無償で共有して評判が上がる |
| 信頼を回復させる | +50〜+150 | 二次被害を先回りした本人通知、誠実な記者会見で炎上が収まる、被害者に寄り添った補償と窓口 |
| 信頼を維持する | +10〜+30 | ガイドラインどおりの当たり前の対応（体制の立ち上げ、証拠の保全、期限内の法定報告） |
| 信頼を傷つける | −30〜−150 | 公表の大幅な遅れ、被害者通知の漏れ、役割を越えた独断、会見での不用意な一言 |
| 信頼を壊す（致命的） | −200〜−300 | 事実の隠蔽、虚偽の発表、証拠を消す初期化、法定の報告を怠る、身代金の支払い |

「維持」の加点は小さくし、「正しくやって当たり前」という現実の空気に合わせる。大きく稼げるのは、当たり前を積み重ねたうえで「回復」と「増やす」に踏み込んだときだけにする。「増やす」の加点は、序盤に致命的な失点があると解放されない。

ただし、事件を宣伝に使う便乗商法（「当社も被害に遇ったからこそ安心」を被害者への対応より先に打ち出すなど）は、「信頼を傷つける」として減点する。売上は信頼の結果としてついてくるものとして描く。

終了時には「信頼スコア」と並べて、「半年後の売上見通し（事件前比）」を表示する。経営者が一番気にする数字で、成果を実感させるためである。

### 細目採点（大雑把な採点を禁止する）

「選択肢を選んだら一発で点が決まる」作りにはしない。同じ「公表する」を選んでも、いつ、誰に、どの言葉で、どの順でやったかで点が変わるようにする。現実の事件でも、差がつくのは細部だからである。

**制作ルール**

- 1シナリオ×1ロールあたり、判断ポイントは15〜25、細目（採点項目）は80以上を目安にする。経営者ロールは判断ポイントを15〜18に抑え、細目は文案作成と記者会見に寄せる
- 1つの判断ポイントは、「大きな方針の選択」と「その実行の細部」の2段で採点する
- 1つの細目の点は±1〜±20に収め、積み重ねで大きな差がつくようにする（致命的な失点と「信頼を増やす」は例外）
- すべての細目に、根拠のガイドライン項目か「実際の事件で問題になった点」を紐づける。制作者の好みだけの細目は作らない
- 終了後の振り返りレポートでは、細目ごとに「取れた点」「取りこぼした点」を全部見せる。「あと1行書いていれば+10だった」が分かることが、もう一度遊ぶ理由になる

**細目の軸（6つ）**

| 軸 | 差がつく細部の例 |
| --- | --- |
| 時刻 | ゲーム内時計は15分刻み。経営への第一報が30分以内か2時間後か、取引先への連絡が報道より先か後か |
| 相手と順番 | 委託元・カード会社・警察・個人情報保護委員会・本人・報道のどれを先にするか。取引先にニュースで知らせたら減点 |
| 言葉 | 「漏えいの可能性」と「漏えいを確認」の使い分け、「被害はありません」の断言、謝罪の主語が「当社」か「委託先」か |
| 中身の抜け | 公表文に発生日時、対象範囲、漏れた項目、本人がすべきこと、問い合わせ窓口、次の報告予定がそれぞれ入っているか |
| 記録 | 判断の時刻と理由を残したか、証拠の保全を誰がいつやったか記録したか（管理の連鎖） |
| 人への配慮 | 対応チームの交代、問い合わせ窓口の人員と想定問答、社員への社内告知と口外施令の出し方 |

**細目の例：No.4 ゴーライドの「第1報を出す」（部門長ロール）**

方針として「第1報を出す」を選んだあと、文案を部品の組み合わせで作らせ、細目ごとに採点する。

| 細目 | 点 |
| --- | --- |
| 検知から24時間以内に出した | +10 |
| 24〜72時間 | +3 |
| 72時間超、または報道が先に出た | −15 |
| 発生と検知の日時を分けて書いた | +5 |
| 対象に「退会者・申込み途中の人」も含むと明記した | +10 |
| 「現会員のみ」と書き、後で訂正した | −20 |
| 「免許証画像」と具体的に書いた（「本人確認書類等」でぼかさない） | +5 |
| 「可能性」と「確認」を正しく使い分けた | +5 |
| 「悪用の事実は確認されていません」だけで終わらせた | −5 |
| 本人がすべきこと（パスワード変更、なりすまし申込みへの注意）を具体的に書いた | +10 |
| 「当社から電話で免許証番号を聞くことはありません」と偽通知への注意を入れた | +8 |
| 専用窓口の電話番号と受付時間を書いた | +5 |
| 窓口に人員を配置せず公表し、電話がつながらない | −15 |
| 次の報告の予定を書いた | +3 |
| 謝罪の主語が「当社」 | +3 |
| 「高度な攻撃により」という言い訳を入れた | −10 |
| 公表前に親会社の広報とIRに文案を共有した | +5 |

全細目を取ると+69、最悪だと−65。同じ「第1報を出す」でも、134点の差がつく。

### 世間の反応（辛辣モード）

判断のたびに、架空のSNS・ニュース・掲示板・業界紙の反応が流れる。ロゴ・媒体名・記者名はすべて架空にする。

- SNS「ツブライン」：「また『現在調査中』か。三日たって何も分からないの？」「免許証預けた俳、もう再発行するしかないんだが」
- ニュース「日刊テックプレス」：「同社は当初『漏えいはない』と説明していた」
- 掲示板：突っ込み、憶測、内部告発っぽい書き込み（真偽不明をどう扱うかも判断対象）
- 社内チャット：現場の不満、疲労、「うちの部署だけ知らされてない」

辛辣さに上限は設けない。批判は実際の報道でよく問われた論点（公表の遅れ、不要なデータの保持、委託先管理、説明の変遷）に合わせる。人格攻撃や差別的な表現は入れない。

### ミスリードの仕掛け（誤対応を誘う声）

現実の事件では、正しい対応をしていても叩かれ、間違った対応が一時的に褒められることがある。本製品では、プレイヤーを誤対応に誘う声を全シナリオに大量に入れる。「批判の量と対応の正しさは関係ない」を体で覚えさせるのが狙いである。

**制作ルール**

- 判断ポイントの半数以上に、誤対応を勧める声を1つ以上入れる。終盤ほど増やす
- 誘導に乗ると、その場では炎上度が下がり、SNSで褒められることもある。代償は数フェーズ後に「遅れて」減点として来る（遅効性ペナルティ）
- 逆に、正しい対応の直後に批判が一時的に増える場面も作る（全停止、早い公表、身代金を拒否した直後など）
- 誘導の声は、正しい声と同じ見た目・同じ長さ・同じ温度で出す。見た目で見分けられないこと
- 振り返りレポートに「あなたを動かした声」を一覧にし、どの声に乗って何点失ったかを見せる

**無難すぎる対応への批判（臆病ゲージ）**

「保留」「様子見」「確定してから」を選び続けると、臆病ゲージがたまる。無難な対応だけでは信頼を「維持」しかできず、「回復」や「増やす」には届かない。

| 臆病ゲージ | 世間の声 | 点 |
| --- | --- | --- |
| 保留2回連続 | 「いつまで『調査中』なんだ」 | −10 |
| 保留3回連続 | 「経営陣は責任を取りたくないだけ」「事なかれ主義の会社」 | −20 |
| 保留4回以上 | 「臆病な経営が被害を広げた」と報道され、取引先が独自に調査を始める | −40 |

ただし臆病批判そのものが罠になる場面もある。「臆病と言われたから」と根拠のない断言や拙速な再開に走ると、もっと大きく失う。大胆さと無謀さの違いを問う。

**ミスリードの型（12種）**

| 型 | 声の例 | 乗るとどうなるか |
| --- | --- | --- |
| 世論 | 「身代金払ってさっさと戻せ。客が困ってるんだ」 | 犯罪組織への支払い。復号も削除も保証されない |
| 臆病批判 | 「一週間も止めてるのは臆病すぎ。他社ならもう再開してる」 | 封じ込めが終わる前に再開し、再感染する |
| 自称専門家 | 「サーバーは全部初期化すれば安全ですよ」 | 証拠が消え、侵入経路も漏えい範囲も分からなくなる |
| 善意の現場 | 「危なそうなので電源を抜いておきました」を褒めるか | メモリ上の痕跡が消える。褒めると同じ行動が広がる |
| 上司の圧力 | 「件数が確定するまで外には出すな」 | 法定の速報が遅れる |
| それっぽい法律 | 「1000件未満なら報告いらないでしょ」 | 不正アクセスなど不正な目的のおそれがあれば件数に関係なく報告対象。報告漏れ |
| ベンダーの都合 | 「弊社の製品に問題はありません。運用の問題です」 | 原因の決めつけ。調査が偏る |
| 攻撃者の揺さぶり | 「24時間以内に連絡しなければ全部公開する」 | 焦った交渉、予定外の公表 |
| 偽の内部告発 | 掲示板の「中の人だけど、本当は10倍漏れてる」 | 未確認の情報に反応して訂正を重ねる |
| 強気でウケる | 「社長、犯人に『絶対許さない』って言ってください。バズります」 | 攻撃者を刺激し、勇場型の応酔が始まる |
| 前回の成功体験 | 他シナリオで正解だった「全停止」を、病院でも即断したくなる | 救急の患者への影響を比べずに止める |
| 褒め言葉 | 「さすが社長、判断が早い。このまま記者会見もやっちゃいましょう」 | 準備なしの会見で、未確認の数字を口にする |

「他のプレイヤーの多くが選んだ選択肢」も画面に出す（初版はデータベースなしのため架空の割合）。正解が一番人気とは限らない。「みんなもそうしてる」も、れっきとしたミスリードである。

### エンディングと爽快感の設計

ランクは、後述の「公式スコア」（素点にプレイ回数の係数を掛けたもの）で決める。

| ランク | 条件 | エンディング |
| --- | --- | --- |
| S | 公式スコア+1200点以上、致命的な失点なし | 事件前より信頼も売上も伸びる。調査報告書が「対応の手本」として業界で引用され、復旧の朝に現場から一言届く |
| A | +600点以上 | 批判は受けたが信頼を取り戻し、売上は事件前の水準に戻る |
| B | +200点以上 | 立ち直るが、大口取引先を失う |
| C | 0〜+199点 | 第三者委員会で対応の不備を指摘され、経営陣が辞任 |
| D | マイナス | 行政指導、集団訴訟、事業撤退。ここから「どこで間違えたか」を振り返る |

爽快感は3つの仕掛けで作る。

1. 記者会見ボス戦：終盤に、辛辣な質問が連続で飛んでくる。それまでに集めた事実と記録が「武器」になり、正しく答えると炎上度が下がる
2. 伏線回収：序盤の地味な判断（ログを守る、時刻を記録する）が、後半の大事な場面で効いてくる
3. 振り返りレポート：終了後、各判断と根拠となるガイドラインを一覧にした「自分だけの事後報告書」を出す。研修の成果物として使える

### プレイ回数の表示と初回補正

何度も繰り返して高得点を取り、それを誇るような使い方を防ぐ。同じシナリオを繰り返せば点が上がるのは当たり前なので、初回の判断を最も高く評価する。

**プレイ回数の表示**

- プレイ回数は、シナリオ×ロールごとに数える
- 「n回目」を必ず表示する。表示する場所は、プレイ中の上部バー、エンディング、振り返りレポート、印刷・保存した振り返り、シナリオ一覧のクリア状況
- 「n回目」の表示は、利用者が消したり隠したりできないようにする
- 例：「No.4 ゴーライド／部門長ロール　3回目のプレイ（係数×0.8）」

**初回補正（公式スコア）**

公式スコアは、素点（その回に積み上げた点）に回数の係数を掛けて出す。

| 回数 | 係数 |
| --- | --- |
| 1回目 | ×1.2 |
| 2回目 | ×1.0 |
| 3回目 | ×0.8 |
| 4回目以降 | ×0.6 |

- 係数は素点がプラスのときだけ掛ける。マイナスのときは素点のまま（繰り返しで失点が軽くならないようにする）
- ランクは公式スコアで決める。同じ素点でも、初回の方が高いランクになる
- シナリオ一覧やクリア状況に出す代表の成績は「初回記録」とする。2回目以降の最高成績は「最高（n回目）」として小さく併記する
- 素点も振り返りレポートに出す。前回より何点伸びたかは、学びの確認として見られるようにする
- 2回目以降のエンディングには、「繰り返しで点が上がるのは当然です。現実の事件に2回目はありません」という一文を添える

**初版の制約**

初版はデータベースを持たないため、プレイ回数はブラウザ内に保存する。保存データを消すと回数も消える。保存データを消すときは「プレイ回数と初回記録も消えます」と確認する。この制約は初版では受け入れる。

### 演出とサウンド（没入感）

BGM・効果音・画面演出を初版から必ず入れる。テキスト主体のまま、プレイヤーが事件の中にいるように没頭できるようにする。

| 要素 | 内容 |
| --- | --- |
| BGM | 場面ごとに変える（タイトル、平常、緊迫、深夜、記者会見、ランク別のエンディング）。炎上度が上がるほど、より切迫した曲に切り替わり、時計の音やざわめきなどの環境音が重なって緊張が高まる |
| 効果音 | SNS・ニュース・社内チャットの通知、電話の着信、攻撃者からのメール、時計の早送り、法定期限の警告、記者会見のシャッター、エンディングのランクの判子など |
| 画面演出 | 通知の雪崩、炎上時の画面の揺れ、深夜帯の暗転、時計の早送り、期限が迫ったときの表示の強調、記者会見のフラッシュ、体力が減ったときの文字のぼかし、状況文のタイプ表示 |

**守ること**

- 正誤を音や演出で先に知らせない。選んだ直後に正解音・不正解音を鳴らさない。誘導の声と正しい声で、音も見た目も変えない（ミスリードの仕掛けを壊さないため）。結果が分かるのは、遅れて来る効果、記者会見、エンディング、振り返り
- 音だけで伝えない。着信や通知は、必ず画面の文字でも伝える。ミュートでも、耳が聞こえなくても遊べること
- BGMと効果音の音量を別々に変えられる。ミュートと「演出を減らす」設定を用意する
- 点滅は1秒に3回以下にする
- ブラウザの自動再生の制限に合わせ、タイトル画面で「はじめる」を押してから音を鳴らす
- BGM・効果音はフリー素材を使う。素材ごとに利用規約を確認し、ゲームでの利用、無料公開での利用、本作の題材が禁止用途に当たらないこと、クレジットの要否、加工の可否、素材単体の再配布の扱いを記録する。規約を確認できない素材は使わない
- クレジット表記が必要な素材は、指定どおりにクレジット画面へ出す。不要な素材も、出典はクレジット画面に出す
- 音声素材はリポジトリのライセンスの対象外とする。素材単体の再配布にならないよう、置き場所は規約に合わせて決める

**プロローグ**　「この事件が報じられたとき、あなたは何と書き込みましたか。」（自由入力。入力例：「公表遅すぎ。自分なら半日でやる」）。続いて「公表まで何時間かかると思いますか」。

**判断1（Day 0、19:40）　部門長から「顧客のサーバーに不正プログラム。範囲不明」と電話**

| 選択肢 | 点 | 結果 |
| --- | --- | --- |
| A. 正確な報告が揃うまで明日の定例会議で聞く | −150 | その夜、顧客の口座で不正取引が続く。「社長は知っていたのに寝ていた」は後で必ず記事になる |
| B. その場で対策本部を立ち上げ、決裁権限を部門長に委譲、外部専門家と弁護士を手配 | +20 | 当たり前の対応。信頼は維持される |
| C. 自分でサーバー室に行く | −50 | 部門長の体力が社長の対応で削られる。「VPNって何？」と聞いた瞬間、過去の講演動画が画面の端に流れる |

根拠：サイバーセキュリティ経営ガイドライン（経営者による体制構築と権限の委譲）。

**判断2（Day 1、04:00）　全サーバーを止めるか**

| 選択肢 | 点 | 結果 |
| --- | --- | --- |
| A. 被害が確認されたサーバーだけ止める | −100 | 別のサーバーでも不正取引が起き、被害拡大ゲージが赤になる |
| B. 全プランを順次停止し、停止の理由だけを告知する | +20 | 被害は止まる。SNSは「使えない」で炎上する |
| C. 全プランを順次停止し、顧客が今すぐすべきこと（取引口座のパスワード変更、セッション切断、証券会社への連絡）を同時に具体的に告知 | +100 | 二次被害を先回りできた。「不便だが、何をすればいいか分かるのは助かる」という声が少しずつ増える |
| D. 全停止するが、告知は「メンテナンス」と書く | −250 | あとで不正アクセスと分かり、「隠蔽」として一番大きく叩かれる。致命的な失点 |

**判断3（Day 1、14:00）　攻撃者から巨額の要求。「支払えばデータは消す」**

| 選択肢 | 点 | 結果 |
| --- | --- | --- |
| A. 支払う | −300 | データが消える保証はなく、犯罪組織に資金を渡した企業として歴史に残る。一週間後、別の攻撃者からも要求が来る |
| B. 支払わないと決め、警察に相談し、決定の理由を公表で説明する | +30 | 攻撃者は情報の一部を公開してくる。そこまでが想定の範囲内 |
| C. Bに加え、公開されたときの被害者への補償方針と専用窓口を先に発表しておく | +120 | 攻撃者の公開が「想定済みの出来事」になり、勇場型の揺さぶりが効かなくなる |
| D. 支払わないが、社長が個人のSNSで「犯人に屈しない」と強い言葉で発信する | −30 | 特定の層には支持されるが、攻撃者が反応して勇場型の応酔が始まる。公式の第几報より社長の投稿の方が引用される |

根拠：警察庁・NISC等のランサムウェア対策の推奨（身代金を支払わない）。

**判断4（Day 3）　個人情報保護委員会への速報**

| 選択肢 | 点 | 結果 |
| --- | --- | --- |
| A. 件数が確定してから報告する | −150 | 速報の期限（概ね3〜5日）を過ぎる。「法定の報告を怠った」と報道される |
| B. 分かっている範囲で速報し、不明点は「調査中」と明記する | +20 | 正解。信頼は維持される |

**終盤：記者会見ボス戦（Day 13）**

質問が5問連続で飛んでくる。「社内から事前に指摘があったというのは本当か」「なぜ2か月半も気づかなかったのか」「見舞金の金額の根拠は」。序盤に時刻と判断を記録していれば、それが答えの材料になる。記録がなければ、答えは「確認しておりません」しか選べない。

1問ごとに、事実に基づく答えは+30、自社の非を認めたうえで具体的な再発防止策まで語れば+80、「答えられない」は−30、責任転嫁や断言しすぎは−100。

**判断5（Day 60）　調査結果をどこまで公開するか**

| 選択肢 | 点 | 結果 |
| --- | --- | --- |
| A. 公開しない（攻撃者に利用されるおそれがある） | −50 | 「結局何だったのか」が残り、解約がじわじわ続く |
| B. 攻撃者に利用される部分だけ伏せ、第三者委員会の報告書を公開する | +100 | 信頼が回復し始める |
| C. Bに加え、再発防止策の進捗を毎月公開し、得た教訓を業界向けに無償で共有する | +300 | 「あの会社が一番学んだ」と評価が反転し、半年後には新規契約が事件前を上回る。ただし序盤に致命的な失点があると、この選択肢は「今さら何を」と受け取られ+50にとどまる |

**エピローグ**　画面に2つのものが並ぶ。左はプロローグで入力した「自分なら半日でやる」。右は、あなたが実際に公表できた時刻。小さく「お疲れさまでした。次に事件が報じられたとき、あなたは何と書きますか。」

## 権利・名誉毀損の配慮

実在の企業の名誉を毀損しないことを最優先にする。サイバー攻撃で悪いのは、常に攻撃した犯罪者である。被害企業は犯罪の被害者であり、本製品はどの企業も「悪役」にしない。皮肉は「外野」に向ける。

### 「悪いのは犯罪者」の注記

対応の巧拙を採点するゲームは、「被害に遭った会社が悪い」という受け取り方を生みやすい。これを防ぐため、次の場所に必ず注記を入れる。

| 場所 | 注記の内容 |
| --- | --- |
| タイトル画面とREADME | 「サイバー攻撃で悪いのは、攻撃した犯罪者です。被害に遭った企業や人を責めるためのツールではありません」 |
| 各シナリオの冒頭 | フィクションであること、実在の団体・人物と関係ないこと、悪いのは攻撃者であること |
| 攻撃者が登場する場面 | 身代金の要求、情報の公開、内部不正などの場面で「これは犯罪です」と明示する |
| 世間の反応 | ゲーム内の批判は、現実に起きがちな反応を再現したもので、制作者の見解ではないこと |
| エンディング（全ランク） | Dランクでも「被害の責任は攻撃者にある。問われたのは被害を広げないための対応だった」と示す |
| 振り返りレポート | 採点は「被害を小さくする対応」の評価であり、被害に遭ったこと自体を評価するものではないこと |
| 解説で実際の事件に触れる箇所 | 実際の被害企業も犯罪の被害者であること |
| スコア・エンディング・振り返りレポート | 高得点が取れても、現実の対応が正しいとは限らないこと。採点は学ぶための目安であること |
| タイトル画面とREADME（目的） | 目的はインシデントレスポンスについて学び、興味を持ち、批判と対応を理解できるようになることで、実在の企業を批判することではないこと |

### 名誉毀損を防ぐルール

- 会社名・サービス名・人物名・ロゴ・商品名はすべて架空にする。実在の商号・登録商標と重ならないか、公開前に確認する
- 実在の経営者の発言をそのまま使わない。記者会見の台詞もオリジナルで書く
- 元事件の数字（件数、金額、日数）はそのまま使わず、規模感だけ合わせて丸めるか変える。実在企業が特定できる組み合わせ（業種＋時期＋件数＋特徴的な出来事）を避ける
- 元事件で未確定のこと（侵入経路、内部の事情）を「事実」として描かない。ゲーム内の架空の設定としてのみ使う
- 「この物語はフィクションで、実在の団体・人物とは関係ありません。サイバー攻撃で悪いのは、攻撃した犯罪者です」を全シナリオの冒頭に表示する。ただしこの表示だけで免責になるとは考えない
- 架空の会社の失敗を描くときも、「愚かな会社」「自業自得」として描かない。判断に迷う人として描き、責めるのではなく学びにつなげる
- 実在の企業の対応を、正解・不正解として採点したり、ランクを付けたりしない。採点の対象は、架空の会社でのプレイヤーの判断だけ
- 「〇〇社の対応は×点」「〇〇社より上手くやれた」のように、実在企業と比べる表示や共有の文言を作らない
- 解説画面で実際の事件に触れる場合は、公式発表と公的機関の資料に限り、出典を示して事実だけを記す。評価や揶揄は書かない
- 報道記事やSNS投稿の文章を転載しない。ゲーム内の反応はすべてオリジナルで作る
- 挿絵はオリジナルまたは利用条件を確認した素材に限る。実在の人物の写真や似顔絵は使わない
- サイバー攻撃や工作に関与する国家は、実在の国名を出さず、すべて「某国」と表記する。制作用の出典欄も含め、本システムの中で北朝鮮などの具体的な国名を使わない
- 国家を扱うシナリオは、政府の公式な注意喚起に基づく範囲にとどめ、特定の国籍や民族への偏見をあおる描写をしない
- 外部の法務レビューは行わない。代わりに、この節の項目を公開前のセルフチェックリストとして、シナリオごとに全項目確認する（本書は法的助言ではない）

## 提供形態と拡張性

初版は、GitHub Pagesで公開するテキスト主体のWebアプリとする。データベースは使わない。ここでは守るべき要件を決める。構成や画面の設計は[概要設計書](basic-design-ja.md)で扱う。

### 提供形態

| 項目 | 要件 |
| --- | --- |
| 形態 | ブラウザだけで動くWebアプリ。ログイン不要 |
| 公開先 | GitHub Pages（静的ホスティングで完結すること） |
| データ保存 | 進行状況（途中経過、点数、プロローグの入力、クリアしたロール）はブラウザ内に保存する。サーバーには送らない。保存データを消すボタンを用意する |
| 表現 | テキストベース。挿絵を入れられる「挿絵スロット」を任意の場面に置ける。挿絵がなくても成立すること |
| プレイ時間 | 1シナリオ×1ロールで30〜60分。経営者ロールは範囲の下限（30分前後）を狙う。4ロールすべてで1シナリオあたり2〜4時間 |
| 記者会見 | 1問ごとに制限時間を設ける（標準30秒、時間切れは「確認しておりません」扱い）。設定で時間を延ばせる |
| 技術 | TypeScript＋Svelte＋Vite でビルドし、GitHub Pages で配信する。シナリオデータは YAML |
| 端末 | PCとスマホの両方で読めること |
| 結果 | 振り返りレポートを画面上で表示し、印刷または保存できること |

### シナリオ更新の仕組み

世間で新しい事件が起きたら、エンジンに手を入れずシナリオだけを差し替え・追加できることを必須要件にする。

- シナリオはエンジンから切り離したデータとして持ち、ファイルを足すだけで一覧に出ること
- シナリオごとに、版、公開日、元事件の発生時期（例：2026年秋の事件を反映）、参照したガイドラインの版、対応言語を持たせる
- 一覧画面に「最新」「定番」「引退」の区分を出す。引退したシナリオも過去問として遊べる
- 正解データはガイドラインの項目に紐づけ、法令や指針が改訂されたら該当する全シナリオを洗い出せること
- シナリオは共通の型（発端・7フェーズ・4ロール・判断ポイント・細目・反応・根拠・皮肉）に従う。一部のロールだけのシナリオも許す

新しいシナリオを出すときの手順は次のとおり。

1. 事件の公式発表、調査報告書、公的機関の注意喚起を集める（報道やSNSは補助としてだけ使う）
2. 事件の「型」と判断の分かれ目を取り出す
3. 会社・人物・数字を架空化し、実在企業が特定できないか確認する
4. 各判断に根拠のガイドラインを紐づける
5. セキュリティの専門家と法務の観点でレビューする
6. 公開し、古いシナリオは引退に回す

目安として、大きな事件が起きてから公式の続報が出そろうまで待ち、その後に公開する。事実が動いている最中に元事件を連想させるシナリオを出さない。

### 多言語対応

- 初版は日本語と英語。画面の文言とシナリオ本文を言語ごとのデータとして持ち、言語データを足すだけで言語を増やせること
- 法令・報告先・期限は国によって違う。英語版は「日本を舞台にした英語版」を初期値にし、将来は法制度パック（例：GDPR、米国州法）を差し替えできる構造にする
- 皮肉や言い回しは直訳せず、その言語で通じる表現に置き換える。翻訳のたびに「特定の実在企業を連想させないか」を確認する
